# Data layout — PostgreSQL / Qdrant / Airflow / RAG

Tier 2 detail for the **Data** section of `context/team-standards.md`. Read this when
changing a schema, writing a DAG, or building an ingestion pipeline.

Anything marked **⚠️ POR DEFINIR** is not settled team convention — ask before assuming it.

## Migrations

- Every schema change ships a **versioned migration** — Alembic (SQLAlchemy/FastAPI) or Django
  migrations. No manual DDL against an environment, and no schema change that only exists in
  the ORM model.
- **The tool writes the migration, not a person.** Alembic revisions come from
  `alembic revision --autogenerate`; Django ones from `makemigrations`. A hand-written revision
  file is a finding: it drifts from the model metadata and skips the checks the tool does.
  Editing an autogenerated revision is fine (and often needed — see below); authoring one from
  scratch is not.
- **Roll out non-breaking**, in separate deploys:
  1. Add the new column/table (nullable or with a default).
  2. Deploy the code that writes and reads it.
  3. Backfill if needed.
  4. Only then drop the deprecated column.
- Index foreign keys and the columns you actually filter on. An index added "just in case"
  costs writes — add it for a query you can name.
- A migration is reviewed like code: it is the hardest change to reverse in production.

### Claude does not generate or apply migrations — the developer runs them

An agent generating migrations is the wrong side of the boundary: `--autogenerate` compares the
models against a **live database**, and the agent rarely has the right one (right branch, right
docker service, right seed state). A revision produced against the wrong head or written by
hand ends up committed, and the next developer inherits it.

So the division of labor is:

1. **Claude** changes the ORM model / schema code, and says explicitly that a migration is now
   pending.
2. **Claude tells the developer the exact command to run**, using whatever this repo actually
   uses — check `Taskfile.yml`, `Makefile`, `docker-compose.yml`, `justfile` or the README
   before guessing. Typical shapes:

   ```bash
   task migrate                                                     # repo task runner (preferred if it exists)
   docker compose run --rm <service> alembic revision --autogenerate -m "add_x_to_y"
   docker compose run --rm <service> alembic upgrade head
   alembic revision --autogenerate -m "add_x_to_y" && alembic upgrade head
   python manage.py makemigrations <app> && python manage.py migrate  # Django
   ```

3. **The developer runs it** and, if needed, pastes back the generated file or the error.
4. **Claude reviews the generated revision** before it is committed: that it contains only the
   intended change (no drift from someone else's model edits), that `down_revision` points at
   the real current head, that `downgrade()` is correct, and that data migrations / backfills
   and index creation are written explicitly rather than left to autogenerate.

The exception is a repo where the migration command is fully local, deterministic and already
approved for use in this session — even then, prefer asking. Never run migrations against an
environment that is not the developer's local one.

## Airflow

- **DAGs are idempotent and re-runnable.** Re-running a task for the same logical date
  produces the same result — no appends that double up, no "already processed" state kept
  only in memory.
- No hidden state carried between tasks. Pass data through a real store or XCom, not
  through module-level variables or files assumed to survive.
- Parametrize by execution date rather than "now", so a backfill behaves like the original
  run.
- Tasks fail loudly. A task that swallows an exception and returns success turns a data
  problem into a silent one.

## RAG / vector ingestion

Ingestion must be **reproducible**: someone should be able to tell, from the repo, exactly
how a stored vector was produced. Always record:

- The **embedding model** (name and version/dimension).
- The **chunking strategy** (size, overlap, split boundaries).
- Any preprocessing applied before embedding.

Changing the embedding model or chunking strategy invalidates existing vectors — treat it
as a migration, not a config tweak, and plan the re-ingestion.

Qdrant collection naming, payload schema, and re-ingestion procedure are per project;
document them in that repo rather than assuming a shared convention.
